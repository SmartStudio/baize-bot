# 生产部署手册

这份手册给负责上线和日常运维的人，按「有哪些进程、迁移、环境变量、单实例、升级回滚、备份恢复」排。每条后面标了代码或配置里的出处。在 Ubuntu 服务器上怎么装、Caddy 怎么写、AppArmor 怎么探、`.env` 每一项的含义，写在 [`deploy/README.md`](../deploy/README.md)。远程电脑的启动文件、安全选项和数据卷写在 [`deploy/remote/README.md`](../deploy/remote/README.md)。这里只引用，不重复。

生产形态就是 `deploy/remote/docker-compose.yml` 这一份 compose，下文的命令都在 `deploy/remote` 目录里跑。凡是标了「未在真机验证」的命令，都还没在 Ubuntu 服务器上跑过。

## 有哪些进程

| 进程 | 跑在哪 | 怎么起 | 出处 |
| --- | --- | --- | --- |
| Postgres 16 | compose 的 `postgres` | `docker compose up -d`，数据在卷 `pgdata` | `deploy/remote/docker-compose.yml` |
| 迁移 | compose 的 `migrate`，一次性 | 每次 `up` 先跑完，成功退出后控制面才起 | 同上，`control-plane.depends_on.migrate` |
| 控制面 | compose 的 `control-plane` | `node --import tsx src/main.ts`，容器里监听 3001，映射到宿主机 `127.0.0.1:${CONTROL_PLANE_PORT:-3201}` | `deploy/remote/Dockerfile` 的 `control-plane` 阶段 |
| Web | 宿主机上的 Caddy，静态文件 | `pnpm --filter @baize/web build`，把 `packages/web/dist` 拷到站点目录 | `deploy/README.md`「Caddy 托管 Web」 |
| 远程电脑 | compose 的 `remote-computer` | 入口脚本起 Xvfb，再 exec 看护进程；看护进程等到启动文件，才起电脑代理，运行器在代理进程里 | `deploy/remote/remote-entrypoint.sh`、`packages/computer-agent/src/supervisor.ts` |
| 用户本机的电脑代理 | 用户的 Mac，不在服务器上 | 桌面端起子进程，启动配置写进 stdin | `packages/desktop/src/main.ts` 的 `spawn` |

控制面一个端口上分出 `/api`、`/api/ws`、`/agent`、`/gateway/v1`、`/hub/v1`、`/mcp-proxy`、`/accounts-proxy`，反向代理要转哪几个见 `deploy/README.md`「电脑的数据面地址跟着它连控制面的地址走」。

控制面不往本地磁盘写数据，`packages/control-plane/src` 里没有 `writeFile`。附件也存在 Postgres 的 `bytea` 里（`packages/control-plane/README.md`「附件」）。所以服务器上要备份的状态只有三样：Postgres、密钥，还有远程电脑的 `bots` 卷，见「备份和恢复」。

不用 compose 时，控制面用 `pnpm --filter @baize/control-plane start` 起，也就是 `tsx src/main.ts`（`packages/control-plane/package.json`）。它只读进程环境，不读 `.env`，变量要由进程管理器注入。

## 迁移

**控制面启动时不跑迁移。** `src/main.ts` 起动只做三步：读两把密钥，拿单实例锁，连库后 `startServer`。`runMigrations` 只有 `src/scripts/migrate.ts` 一处调用，测试之外没有别的调用方。库没迁移到位，控制面也不会自己补。

**谁来跑。** compose 里是一次性服务 `migrate`，每次 `docker compose up -d` 都跑一遍，已跑过的跳过。不用 compose 时，在新版本的代码目录里手动跑：

```
DATABASE_URL=postgres://... pnpm --filter @baize/control-plane migrate
```

迁移脚本和控制面一样只读进程环境（`src/env.ts` 的 `databaseUrl`），不读 `.env`。不带 `DATABASE_URL` 时它落到默认的 `postgres://baize:baize@localhost:5434/baize`。

**机制。** `src/db/migrate.ts` 按文件名顺序应用 `packages/control-plane/drizzle/*.sql`，跑过的记在 `_migrations` 表里。待跑的迁移在同一个事务里执行，事务开头拿一把事务级咨询锁，两个迁移进程并发时后到的排队。中途失败整批回滚，库停在迁移前的样子。输出是「应用了 N 个迁移: ...」或「迁移已是最新，没有要跑的」。

**什么时候跑。** 升级时跑，时机是旧控制面停掉之后、新控制面起来之前。有三点原因：

- compose 的 `depends_on` 只保证新的控制面容器等 `migrate` 成功后才起，不保证先停旧的。旧控制面在迁移期间和迁移之后可能还连着库。
- 迁移的咨询锁（`migrate.ts` 的 `MIGRATION_LOCK`）和控制面的单实例锁不是同一把，控制面在跑时迁移照样能进去。
- 有的迁移删列，旧代码跑在新表结构上会出错，删了哪些列见 `deploy/README.md`「迁移」。`0023` 还明确要求先停完旧实例再迁移（`packages/control-plane/README.md`「迁移 0023 和部署顺序」）。

所以升级步骤里先 `docker compose stop control-plane`，再 `up -d`，见「升级」。

**耗时长的迁移。** `0036`、`0037` 会整批回填 `work_entries`，行多的时候表会锁很久。升级前先按 `deploy/README.md`「迁移」里的命令数一下要回填的行，再按那里的实测表估时间。

## 环境变量和密钥

控制面读哪些变量，以 `packages/control-plane/src/env.ts` 为准，`src` 里只有这一个文件读 `process.env`。compose 传哪些、默认值是什么，全表在 `deploy/README.md`「`.env` 清单」，写在 `deploy/remote/.env` 里，不提交。

**缺了起不来的。**

| 变量 | 谁拦 | 说明 |
| --- | --- | --- |
| `TOOL_SECRET_KEY` | 没设：`env.ts` 的 `toolSecretKey`，`main.ts` 在拿单实例锁之前就拦下。格式不对：`startServer` 里 `new ToolCrypto` 时拦（`src/crypto.ts`），这时已经拿了锁、连了库 | 64 位十六进制，`openssl rand -hex 32` |
| `CREDENTIALS_KEY` | 没设：`env.ts` 的 `credentialsKey`，同上。格式不对：`startServer` 里 `new CredentialCrypto` 时拦（`src/credentials.ts`），同上 | 32 字节 base64，`openssl rand -base64 32` |
| `UPSTREAM_BASE_URL`、`UPSTREAM_API_KEY` | compose 的 `${...:?}` | key 只能是可打印 ASCII，否则控制面起动时抛错（`env.ts` 的 `upstreamApiKey`） |
| `WEB_BASE_URL` | compose 的 `${...:?}` | OAuth 回调拼在它上面 |

格式写错同样起不来：`GATEWAY_MODELS` 缺用途、GitHub 的 `GITHUB_APP_CLIENT_ID` 和 `GITHUB_APP_CLIENT_SECRET` 只设了一个、X 设了 `X_CLIENT_SECRET` 却没设 `X_CLIENT_ID`、`PORT` 或 `TRUSTED_PROXY_HOPS` 不是数，都在 `env.ts` 里抛错。X 只设 `X_CLIENT_ID`、不设 secret 是允许的（`env.ts` 的 `oauthConfig`）。

**密钥。** 下面这些是机密，只放在 `deploy/remote/.env` 里，文件权限给 600：

- `TOOL_SECRET_KEY`、`CREDENTIALS_KEY`：库里的工具凭据和平台账号令牌是用它们加密的。换了或丢了，已存的密文全部解不开。数据库备份里只有密文，**这两把要和备份分开、另外保管一份**，不然备份恢复回来也用不了这些凭据。
- `UPSTREAM_API_KEY`：只在控制面进程里，电脑拿到的是控制面发的网关 key（`docs/开发.md`「控制面」）。
- `GITHUB_APP_CLIENT_SECRET`、`X_CLIENT_SECRET`：两家 OAuth 应用的 secret。
- `POSTGRES_PASSWORD`：compose 不设时是 `baize`（`docker-compose.yml`），生产要换。

**不能进电脑代理环境的。** `COMPUTER_ID`、`AGENT_TOKEN`、`CONTROL_PLANE_AGENT_URL`、`BAIZE_DATA_DIR` 这四个名字不能出现在代理或看护进程的环境里，身份只走一行 stdin JSON `{ url, computerId, token, dataDir }`：

- 远程电脑的看护进程看到其中任何一个，直接拒绝启动（`packages/computer-agent/src/supervisor.ts` 的 `FORBIDDEN_ENV`）。身份由 `./put-launch.sh` 写成启动文件放进容器（`deploy/remote/README.md`「启动文件」）。
- 电脑代理自己看到 `AGENT_TOKEN` 也拒绝启动（`packages/computer-agent/src/main.ts` 的 `readLaunch`）。
- 桌面端只按白名单把 `PATH`、`HOME` 这类几个变量传给代理（`packages/desktop/src/main.ts` 的 `AGENT_ENV_KEYS`、`agentEnv`）。`pnpm dev --agent` 起代理前把这四个名字从子进程环境里删掉（`scripts/dev.mjs` 的 `agentEnvKeys`、`agentEnvOf`）。

`remote-computer` 服务在 compose 里没有 `environment` 段，控制面的变量和密钥都到不了它。往这个服务加环境变量时，别把上面四个名字和控制面的密钥加进去。

## 单实例

**同一个库上只能跑一个控制面。** 几样状态只在进程内存里：电脑连接表（`src/agent/hub.ts` 的 `AgentHub`）、画面中继（`src/live/relay.ts`）、多 Bot 群回合（`src/agent/group-turn.ts`）、登录注册的限频计数（`src/http/auth-limits.ts`）、免打扰期间攒着的通知（`src/notifications.ts`）。起两个实例，电脑连在甲上、浏览器推送连在乙上，派活和推送就会丢。

**第二个实例为什么起不来。** 控制面起动时，先在一条专用的库连接上拿会话级咨询锁 `pg_try_advisory_lock(0x627a6370)`（`src/instance-lock.ts`）。拿不到就抛错「同一个库上已经有一个控制面在跑」，`main.ts` 打印「控制面没起来」后以 1 退出。这一步在监听端口之前，所以第二个实例不会接到任何请求。这条连接关掉了 `max_lifetime` 和 `idle_timeout`，不会被连接池轮换掉。连接一断，锁就放了，控制面按停机流程以 1 退出，compose 的 `restart: unless-stopped` 把它拉起来重新拿锁。

所以：

- 不要 `docker compose up --scale control-plane=2`。第二个容器会一直在「起不来，重启」里循环。
- 不要用先起新、再停旧的滚动升级，新的那个拿不到锁。按「升级」里的步骤先停再起。
- 停机流程和探活接口 `GET /api/health` 见 `deploy/README.md`「单实例、停机和探活」。

## 升级

升级前先看 `deploy/README.md`「升级顺序」：改了报文形状的版本，要先发桌面端新版，再升控制面。

```
cd deploy/remote
git rev-parse HEAD >> ~/baize-deployed-commits      # 记下现在跑的版本，回滚时用
git pull                                           # 或者 checkout 到要上的那一版。只换宿主机上的文件，跑着的容器不动
docker compose build                               # 只出新镜像，库和跑着的容器都不动
./backup-db.sh                                     # 必须在 up 之前，up 会自动迁移。它会打印库停在哪条迁移
docker compose stop control-plane                  # 旧控制面先停，见「迁移」里的原因
docker compose up -d                               # migrate 跑完，新控制面才起
docker compose logs migrate                        # 应有「应用了 N 个迁移」或「迁移已是最新」
curl -fsS --retry 10 --retry-delay 1 --retry-all-errors http://127.0.0.1:3201/api/health   # 应回 {"ok":true}，端口按 CONTROL_PLANE_PORT
./put-launch.sh [账号邮箱]                          # 远程电脑容器重建后要重新放启动文件
```

整段未在真机验证。几处顺序的原因：

- `git pull` 在备份之前，因为旧版本里没有 `backup-db.sh`，第一次升级到带它的版本时，代码拉下来才有这个脚本。`git pull` 和 `build` 都不碰库和跑着的容器，`up -d` 才换容器、跑迁移。
- `build` 也在备份之前。备份到 `stop` 之间旧控制面还在写库，这些数据不在备份里，回滚时会丢，见「回滚」。构建挪到前面，这段就只剩备份本身加上停控制面的时间。`pg_dump` 导的是开始那一刻的快照，导的过程中写进去的也不在里面。
- 新控制面刚起来时端口可能还连不上，或者回 503，所以 `curl` 带重试。用 `--retry-all-errors` 而不是只重试连接被拒，是因为 docker 的端口转发在容器还没监听时可能先接下连接再断开，这一点是推断，没实测。这个选项要 curl 7.71 以上，Ubuntu 22.04 自带的是 7.81。

`put-launch.sh` 为什么每次都要重跑，见 `deploy/remote/README.md`「启动文件」。

`migrate` 失败时，`docker compose ps` 里它是非 0 退出，新控制面不会起。迁移在一个事务里，失败时库停在迁移前的样子。这时不用恢复备份，按下面「回滚」的步骤走，跳过 `restore-db.sh` 那一行，只把代码换回旧版本、重新构建再起。

## 回滚

新代码不能跑在没迁移过的库上，旧代码也不保证能跑在迁移过的库上，因为有的迁移删列。所以回滚是旧代码加升级前的备份一起换回去。**备份之后写进库的数据都会丢**：升级之后新版本写的，加上备份到停控制面之间旧版本写的。回滚前要想清楚。

```
cd deploy/remote
docker compose stop control-plane
./restore-db.sh --replace ~/baize-backups/baize-<升级前那一份>.dump baize
git checkout <~/baize-deployed-commits 最后一行>   # 恢复要在换代码之前做，旧版本里可能没有 restore-db.sh
docker compose build
docker compose up -d                               # migrate 对着恢复回来的 _migrations，应当没有要跑的
docker compose logs migrate
curl -fsS --retry 10 --retry-delay 1 --retry-all-errors http://127.0.0.1:3201/api/health
./put-launch.sh [账号邮箱]
```

整段未在真机验证。确认无误后，删掉 `restore-db.sh` 留下的原库，删的命令它会打印出来。

## 备份和恢复

**要备份的。**

| 什么 | 在哪 | 怎么备 |
| --- | --- | --- |
| 业务数据，含附件 | Postgres 的 `baize` 库 | `deploy/remote/backup-db.sh`，见下 |
| `TOOL_SECRET_KEY`、`CREDENTIALS_KEY` | `deploy/remote/.env` | 另外保管一份，不和数据库备份放一起，原因见「密钥」 |
| 远程电脑上的 Pi 会话、Chrome 登录态、批准装的 Python 包 | 卷 `baize-remote_bots` | 仓库里没写脚本，见本节最后 |

skill 文件不用单独备，它以控制面的 `skills` 表为准，随 `config` 重新下发到电脑上。用户本机的 `~/.baize/bots` 在用户自己手里，服务器管不到。

**备份脚本。** `deploy/remote/backup-db.sh` 用 `pg_dump -Fc` 导出成 `<库名>-YYYYmmdd-HHMMSS.dump`。导完用 `pg_restore --list` 核一遍能读，再从临时名改成正式名。坏文件不会挤掉旧的好备份。之后它按文件名里的时刻只留最近 `BACKUP_KEEP` 份。文件权限是 600，库里有密码哈希和加密过的凭据。`pg_dump` 在一个快照里导，控制面在跑时也能备。

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `BACKUP_DIR` | `~/baize-backups` | 备份放哪 |
| `BACKUP_KEEP` | `14` | 留几份，不带前导零的正整数。`0`、`00`、`08` 都拒绝 |
| `DB_NAME` | `baize` | 导哪个库 |
| `PG_CONTAINER` | 空 | 设了就直接 `docker exec` 这个 Postgres 容器，不经 compose |

每天凌晨三点备一次的 crontab（未在真机验证）。日志重定向在脚本建目录之前就要打开文件，所以先把目录建好：

```
mkdir -p ~/baize-backups
```

```
0 3 * * * cd /path/to/baize-bot/deploy/remote && ./backup-db.sh >> "$HOME/baize-backups/backup.log" 2>&1
```

脚本只把备份写在本机。服务器磁盘坏了，本机的备份跟着没，要自己再同步一份到别的机器。

**恢复。**

```
./restore-db.sh [--replace] <备份文件> <目标库>
```

- 先建 `<目标库>_restoring`，用 `pg_restore --single-transaction --exit-on-error` 整份灌进去。灌失败，或者灌完发现又有连接连上了目标库，都删掉这个临时库，原库不动。原库已经改了名之后再出错，临时库就留着，里面是恢复好的那一份。被 Ctrl-C 或 SIGTERM 打断时（Ubuntu 的 `/bin/sh` 是 dash，打断时不跑清理），临时库也会留下，下次恢复会被拦住并给出删除命令。
- 灌成了，再把原库改名成 `<目标库>_before_<时刻>` 留着，把临时库改名成目标库。原库要等确认无误后自己删，删的命令脚本会打印出来。
- 目标库已经存在时必须带 `--replace`。还有连接连着目标库时拒绝动手，提示先 `docker compose stop control-plane`。
- 不用 `pg_restore --clean`：它只删备份里有的对象。备份之后的迁移建的表会留下来，`_migrations` 却恢复成了旧的，下次升级重跑那条迁移就撞上同名的表。整库替换没有这个问题。
- 最后打印恢复出来的库有几张表、几条迁移记录、最后一条迁移是哪个，和备份时打印的那一行对得上就对。

**本机验证记录。** 2026-10-25 在开发机的 Postgres 16（容器 `baize-postgres`）上，用 `PG_CONTAINER=baize-postgres`，只对工作树自己的库 `baize_ops_deploy_docs` 和临时建的库跑过：

- 连备三次，`BACKUP_KEEP=2`，最早那份被删，剩两份。打印「41 张表，迁移 50 条，最后一条 0049_turn_persist.sql」。
- 恢复到新库，打印同样的三个数。两个库的表名清单、`_migrations` 清单逐项一致，`users`、`bots`、`computers` 行数一致。
- 目标库已存在、不带 `--replace`：拒绝。有一条 psql 连着目标库时 `--replace`：拒绝，提示先停控制面。拿一个坏文件恢复：`pg_restore` 报错，临时库删掉，原库不动。
- 在目标库里先建一张多出来的表、插一条多出来的迁移记录，模拟升级后的库，再 `--replace`：多出来的表和记录都不见了。
- 第二轮在临时库 `baize_verify113_*` 上，`sh` 和 Ubuntu 默认的 `dash` 各跑一遍：`BACKUP_KEEP` 为 `00`、`08`、`0`、`2x` 都拒绝，退出码 1，已有的备份一份没少。为 `2` 时连备三次剩两份。
- 恢复时让一条连接在 `pg_restore` 期间连上目标库：灌完后的第二次检查拒绝，临时库删掉，原库不动，再恢复不会被「临时库已经存在」拦住。
- 验证完，临时建的库全部删掉。

经 compose 的路径，也就是不设 `PG_CONTAINER`、走 `docker compose exec -T postgres` 的那条，未在真机验证。

**`bots` 卷。** 仓库里没有备份它的脚本。要备的话，先停 `remote-computer`，避免 Chrome 和 Pi 正写到一半，再把卷打包出来（未验证）：

```
docker compose stop remote-computer
docker run --rm -v baize-remote_bots:/data:ro -v "$HOME/baize-backups:/backup" node:22-bookworm-slim \
  tar czf "/backup/bots-$(date +%Y%m%d-%H%M%S).tgz" -C /data .
docker compose start remote-computer
./put-launch.sh [账号邮箱]
```

## 电脑代理的发件箱

#47 提过发件箱没有大小上限。#91（PR #103）补上了单帧上限：可靠上行进 `ReliableOutbox.append` 之前按 `AGENT_FRAME_MAX_BYTES`（16 MiB，`packages/shared/src/protocol.ts`）截短，截不下的拒收，不再因为一帧超限把整个发件箱卡死（`packages/computer-agent/src/frame-limit.ts`、`reliable-transport.ts`）。

帧数和总字节数仍然没有上限，也没有淘汰策略，总量上限拆到 #115 跟进。控制面只认连续的序号，删掉中间的帧，后面的帧全成缺号（`reliable-transport.ts` 里旧帧截短那段的注释）。发件箱在 `<dataDir>/.agent/outbox/`，控制面确认之后就压缩掉已确认的帧。派活走下行，断线期间不会有新 run 派进来。电脑长期离线时要看的是这个目录的大小，在服务器上就是 `bots` 卷下的 `.agent/outbox/`。
