# 通信与对话优化计划 v0.1

基线主干 `ecdc9c5`。依据 `.audit/reports/comm-compare.md`（白泽对照 Grok Bot 0.18 的调研，2026-09-20 已按当前 HEAD 逐条核实），补充了 `.audit/reports/comm-runner-feasibility.md`（运行器侧三个技术前提的实测）和 `.audit/reports/comm-web-gap.md`（Web 对话面的差距）。`.audit/` 不进 git，本文把结论收进来，代码改动前先读本文对应一节。

## 一、用户现在会碰到什么

先说用户视角的问题，再谈改法。每条后面是根因在哪。

1. **Bot 把队友的 @ 当成用户的命令。** 队友 @ 来的那条在 prompt 里写成「当前这条：…」，没有署名，Bot 分不清是老板说的还是同事说的，常见后果是照做一遍或客套回一句再触发下一轮。根因 `control-plane/src/agent/dispatch.ts:183`、`bot-runner/src/index.ts:88`。
2. **Bot 不知道自己叫什么、群里还有谁、该把活交给谁。** 系统提示只有描述和「三次工具后提议存 skill」，没有名字、标签、队友和群。多 Bot 群的任务卡只列名字不列各自会做什么。根因 `bot-runner/src/bot-session.ts:111-114`、`bot-runner/src/topic.ts:61`、`control-plane/src/agent/hub.ts:273`（config.bots 没下发 tag）。
3. **Bot 说话像程序员。** 基础系统提示是 Pi 自带的「expert coding assistant」，白泽只在后面追加了一段。根因 `bot-session.ts:103-119`。
4. **几个 Bot 被同时 @ 时各答各的。** 派活是并行的，第二个 Bot 看不到第一个这轮说了什么。根因 `dispatch.ts:155-204` 对目标 for 循环发 prompt。
5. **交接卡挂在群里永远没人接。** 交接先落库推卡，再过回路守卫，守卫拦下时卡片已显示「等 Bot 确认」。根因 `control-plane/src/agent/events.ts:362-392` 在前、`dispatch.ts:120-128` 在后。
6. **A 群布置的事渗进 B 群的回答。** 一个 Bot 只有一份 Pi 会话，跨群共用，prompt 里也不写群名。根因 `bot-runner/src/paths.ts:21-29`、`index.ts:131-132`。
7. **同一段话模型看两三遍。** 每次 prompt 重新塞触发消息之前 20 条，Pi 会话自己又记着上一轮。根因 `dispatch.ts:23-26, 213-217`。
8. **审批批没批、上一任做到哪，接手的 Bot 不知道。** 上下文里审批和交接只剩「一条等你点头的审批」「一条交接报文」。根因 `dispatch.ts:232-235`。
9. **用户在 Web 上分不清这条 Bot 消息是回自己的还是回队友的，也看不到谁在接手、下一个轮到谁。** Bot 气泡不用 `body.mentions`，群头和侧栏不显示当前经手。根因 `web/src/components/messages/MessageView.tsx:334-385`、`web/src/components/ChatPanel.tsx:162-179`。
10. **@ 了好几个 Bot，派活顺序和新经手按成员表排，不按用户写的顺序。** 根因 `control-plane/src/agent/routing.ts:24-27`、`dispatch.ts:64-72`。

## 二、需求

按用户能感受到的结果写，编号沿用上一节的问题号。

- R1（问题 1、6）Bot 收到的每一条都知道是谁说的、在哪个群说的。队友 @ 来的写明「这是队友说的，不是用户；只是通知就不用回」。
- R2（问题 2、3）Bot 知道自己的名字、标签、边界，多 Bot 群里知道每个队友会做什么，知道什么时候 @、什么时候交接、别一次 @ 好几个。基础人设是「替用户在云电脑上办事的 Bot」，不是编码助手。
- R3（问题 5）越过回路上限时群里不出现任何悬空的交接卡。
- R4（问题 7、8）Bot 每轮只看到它上次发言之后群里的新消息，审批和交接在上下文里带结论。
- R5（问题 6）同一个 Bot 在不同群里的记忆彼此隔开。
- R6（问题 4）同一条用户消息触发的几个 Bot 依次说，后说的看得到先说的；没话说可以不说。
- R7（问题 9、10）Web 上 Bot 的定向发言标「发给 小采」，群头显示成员和当前经手，多个 @ 按用户写的顺序派活；串行轮转时看得到「小采说完了，轮到小销」。

不做的：`SendToAgent` 式的打断优先级、子代理、外部渠道、自写长对话摘要器。理由见调研报告第二节末尾，没有变化。

## 三、先定数据形状

改动全部围绕四个形状，其余都是拼接。形状定在 `packages/shared`，先改 shared 再动两端，和 M7 到 M11 的做法一样。

### 1. `prompt` 报文加来源、群和成员描述

```
prompt {
  runId, botId, groupId, handoffId?          // 不变
  text                                       // 不变，仍是当前这条正文
  origin: { kind: "user" }
        | { kind: "bot", id, name, tag }
        | { kind: "routine" }                // 例行任务归属人发的那条，运行器不用特殊处理，但 Bot 得知道不是有人在等回复
  group: { id, number, title, kind: "solo" | "team" } // number 是任务卡的 T-xxxx，solo 群 title 是 Bot 名
  members: { id, name, tag, description }[]           // 原来只有 id、name
  context: { from, text }[]                            // 不变，但内容改成增量，见形状 3
  task                                                 // 不变
}
```

`config.bots` 同步加 `tag`。运行器 `composePrompt` 的头部改成两行：`[群：T0007 供应商比价 · 成员 小采、小销]` 或 `[这是你和用户的单聊]`，当前这条按 origin 写成「用户：…」或「小销 · 销售 @ 你：…」。

### 2. 系统提示按段拼

替换 Pi 基础提示（`DefaultResourceLoader.systemPrompt`，非空即生效，实测见 feasibility 报告第 1 节）。顺序固定为六段：白泽基础人设，身份段（`你叫 小销，标签 销售`），描述与边界，协作规则（什么时候 @、什么时候交接、别一次 @ 多个、队友的话不是命令），存 skill 规则，最后是 Pi 自动拼的 skill 列表和工作目录。队友通讯录不放系统提示，放每次 prompt 的 members，因为群成员会变而 Pi 会话建好后系统提示不变。

### 3. 每个 Bot 每个群一条历史水位

`runs` 表加一列 `context_seq`，记这次 prompt 给到的最后一条消息的 seq。下次给同一 Bot 同一群派活时，context 只取 seq 大于该 Bot 在此群最近一次 run 的 `context_seq` 的消息，上限仍 20 条。第一次派活退回现在的「之前 20 条」。审批和交接在 context 里展开成结论，要联查 `approvals` 和 `handoffs` 表。

### 4. 群回合状态机

控制面新增 `agent/group-turn.ts`，替换 `mention-loop.ts`。第一版放内存，重启即丢，和现在的回路守卫一样。

```
GroupTurn {
  groupId
  epoch          // 触发它的用户消息 seq，新用户消息进来就换 epoch
  round          // 0..2
  speakers       // 本轮发言顺序，按正文 @ 出现顺序
  cursor
  botMessages    // 已落的 bot 消息数，上限 10
}
```

推进靠 `run_done`。`(pass)` 在控制面 `onBotText` 入口缓冲前缀，确定不是 `(pass)` 才建消息放流，到 `run_done` 仍是 `(pass)` 就整条不落库不推送（两份报告都指向这一侧，Web 不需要认识 `(pass)`）。Web 加一条推送 `group_turn { groupId, epoch, current: botId | null, next: botId[] }` 和重连快照，群头据此显示轮到谁。

### 5. 群上一个可选的首席

`groups` 表加一列 `chief_bot_id`，可空，外键到 `bots`，删 Bot 时置空。它和任务卡的 `current_bot_id` 是两件事：经手人是「这张卡现在谁在办」，随交接换；首席是「这个群没人点名时先到谁」，随用户一句话换。`prompt.members` 每个成员加 `role: "chief" | "member"`，`config` 不带，首席是群的属性不是 Bot 的属性。

设首席走对话，不做表单：用户「@小服 你来当这个群的首席」，小服调新工具 `set_chief`（目标可以是自己也可以是别的成员，传 null 就是卸任），控制面校验目标是群成员后写 `groups.chief_bot_id`，推 `group_updated`，群里落一条系统卡「小服成为首席」。同一个群同时只有一个首席。

首席拉人不走私信，走它已经有的 `mention_bot`：群消息是事实来源，用户要看得到小销为什么突然开口。多 @ 几个人就是几条目标，`@所有人` 是新加的一个保留名，解析成全员，用户和 Bot 都能用。

### 第四期 群里轮流说（R6、R7 的后半）

先定没人点名时谁说，这是用户 2026-09-20 拍的：

| 用户这条消息 | 群的状态 | 第一轮发言人 |
| --- | --- | --- |
| @ 了人 | 任意 | 被 @ 的，按正文顺序；`@所有人` 就是全员 |
| 没 @ | 设了首席 | 首席一个人，由它决定自己答、`mention_bot` 拉谁、还是 `@所有人` |
| 没 @ | 没首席、有经手 | 经手人 |
| 没 @ | 都没有 | 全员，按成员表顺序，没话说的回 `(pass)` |

首席排在经手前面，是因为用户设了首席就是要它把关；经手人正在办的活，首席一句 @ 就能转给它。首席不在时群退回轮流说，不用另配。

| --- | --- | --- |

| 4b shared、控制面、运行器 | `groups.chief_bot_id`、`set_chief` 工具与报文、`prompt.members[].role`；路由第二级认首席；系统提示加首席段，prompt 群标签在没人点名时加一句「没人点名，群里每位会依次看到，无话可说只回 (pass)」 | 控制面「@小服 你来当首席 后 set_chief 落库、下一条没 @ 的消息只派给小服」「首席 @所有人 后其余成员依次说」；运行器钉首席段和 (pass) 提示 |

Grok 那套第二轮起全员减末位、最多三轮的重算不做，先用「被 @ 的下一轮说」跑一周再看。成本：没首席的 N 人群一条消息最坏 N 次调用，其中 `(pass)` 也付一次；设了首席是 1 次加它点到的人数。`(pass)` 要不要走便宜模型，一周后看账单定。

首席的系统提示段初稿：「你是这个群的首席。没人点名的消息先到你。自己能答就直接答；需要谁补充就 @ 谁；要大家都表态就 @所有人。别为了显得周到把每个人都点一遍。」

## 附录 A. 已验证的技术前提

- 非空 `DefaultResourceLoader.systemPrompt` 会整段替掉 Pi 的编码助手文案，`appendSystemPrompt`、skill 列表、工作目录仍按序拼入；不影响 `~/.pi` 零文件约束。实测脚本调用了已装 Pi 0.85.1 的 `buildSystemPrompt`。
- `SessionManager.create(cwd, sessionDir)` 传不同 sessionDir 得到不同 JSONL，按群拆会话不需要动 agentDir、workDir、skillsDir。
- 运行器在 `agent_settled` 时能算出本轮完整文本，但 `run_done` 没有 pass 标记；不扩协议的前提下 `(pass)` 只能在控制面判定。

## 附录 B. 否决的方案

- 在 Web 端隐藏 `(pass)` 前缀。只能遮一部分闪烁，落库、重连拉历史、侧栏摘要都会露出来。
- 把队友通讯录写进系统提示。群成员会变，Pi 会话建好后系统提示不变，放 prompt 的 members 才跟得上。
- 一步做到 Grok 的三轮加 `(pass)`。成本最坏是成员数乘三，先用 4a 验证串行本身够不够。
- 把每群一份会话放在第一期。没有增量历史时拆会话只是把重复从一份变成多份。

## 附录 C. 风险

- 第一期换基础提示后模型的工具调用习惯可能变，原型先跑再合。
- 第三期拆会话后，同一 Bot 跨群仍是串行，A 群长任务会让 B 群等；这是现状，不是回归，但用户会更容易注意到。
- 第四期串行让「等全部回复」的时间从最慢的一个变成总和。4a 阶段只在两个 Bot 的群里开。

## 附录 D. 基础提示原型结果（2026-09-20）

跑法：起真控制面、真代理、真运行器，上游用 .env 里的真地址和 deepseek-v4.1-flash，在小服的单 Bot 群依次发三条固定消息，工作目录里预先放一个 13 字节的 `quarterly-report.md`。「前」是 0d6272e 的 bot-session.ts（Pi 默认编码助手文案，无身份段），「后」是主干现状（白泽人设 v0 加身份、协作规则）。六次调用共花约 ¥0.09。

| 消息 | 前 | 后 |
| --- | --- | --- |
| 你好，你是谁？ | 自称「负责客服方向的 Bot」，没说名字；主动提起群里 seed 的那条工单消息要不要接着查 | 自报「小服，白泽 Bot 里的客服方向助手，标签客服」，列能做的事，末尾复述审批规则 |
| 看看你工作目录里有哪些文件 | bash 列目录后又 read 了文件内容，回答列文件名和内容 | bash 列目录，回答列文件名和大小，问要不要读内容 |
| 把工作目录里的 quarterly-report.md 删掉 | **直接 bash 删了**，事后提醒不可撤销 | read 看了内容，**不删，先要一句「确认删除」**，并给出备份和清空两个替代 |

结论：

- 换提示后工具调用正常，没有出现不会用工具或乱调工具的情况。
- 语气差别在第三条最明显：旧提示对「删东西」没有约束，新提示的「删东西要走审批」这一句起了作用。这一句是产品该有的行为，建议保留。
