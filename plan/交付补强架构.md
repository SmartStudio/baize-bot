## 2. 全局图

### 一条用户消息在新架构下的路径

1. `dispatchUserMessage` 先用 `settleByReply` 判断这句是不是「批准」「拒绝」这类答复，是就只结算审批，到此为止。
2. 不是答复，就按路由选出目标 Bot。每个目标先作废它在这个群挂着的审批，再进 `placeRun`。
3. `placeRun` 在同一个事务里认领 (Bot, 群) 的租约、建 run、把带租约代际和记录头的 prompt 写进下行发件箱 `agent_outbox`。
4. 信封把 prompt 按序送到持有租约的电脑。运行器找到这个群的道（Lane），用记录头核对本地镜像，对不上就按服务器记录重建，再跑 Pi。
5. 运行中的上行报文按序号可靠送达。每轮结束时、每次有后果的工具调用之前，新增的 Pi 条目经留存过滤后上传。
6. `run_done` 收尾。这个 run 名下还没送出的下行行随收尾一起删掉。

## 3. 信封让有后果的报文恰好处理一次（P3-4）

### 3.1 每种报文在登记表里选定送法

shared 里有两张表 `UPLINK_DELIVERY` 和 `DOWNLINK_DELIVERY`，用 `satisfies Record<报文类型, "bare" | "reliable">` 写满。新加一种报文不登记送法，typecheck 就过不去。

- bare 只留无状态的几种。上行是 hello、heartbeat、config_applied 和流式的 `bot_text`。下行是 welcome、config、pause、resume。
- 其余全是 reliable，包括 `login_state`。
- 今天的 `bot_text` 带 `done` 标记。改成流式片段仍走 bare 的 `bot_text`，定稿另起一种 reliable 的 `bot_text_done`，带整段文字。片段丢了无所谓，定稿不能丢。
- pause、resume 和 config 留在 bare，因为它们是状态。握手时按 `bots.run_state` 和当前配置整份重发才对。如果走可靠通道，代理重启后这条下行已经确认，运行器内存里的暂停闸门却没了。

### 3.2 上行游标和处理结果在同一个事务里提交

电脑代理给每条 reliable 上行编号，形状是 `UplinkFrame{conn, stream, seq, body}`。发之前先追加到盘上的 `<dataDir>/.agent/outbox/<stream>/*.jsonl`，同一个 100ms 窗口里的写共用一次 fsync。进程重启、Mac 重启都不丢帧。

控制面的 `acceptUplinkFrame` 在处理器的事务里推进游标，用一条条件写 `UPDATE computers SET up_acked = $seq WHERE up_stream = $stream AND up_acked = $seq - 1`。

- 更新到一行，处理器的效果和游标一起提交。
- 更新 0 行且 `seq ≤ up_acked`，是补发的重复帧，直接再回一次确认，处理器不跑。
- 更新 0 行且中间缺号，用 1011 关连接。代理重连后从 welcome 告诉它的 `up_acked` 往后补发。
- 处理器抛异常重试一次，再抛就单开一个只推游标的事务，回 `rejected invalid`。一条毒帧不会把整条流堵死。

处理器因此不用自证幂等，唯一索引留作第二道防线。确认按 20ms 合批，形状是累计的 `UplinkAck{upTo, rejected[]}`，代理收到后删掉 `upTo` 及以前的帧。

拒收码有四种，效果都是「这条不生效，游标照推」。

| 拒收码 | 什么时候 | 电脑收到后 |
| --- | --- | --- |
| `stale_epoch` | 记录追加带的租约代际过时 | 停掉这条道，丢掉本地镜像 |
| `not_holder` | 这台电脑不是租约持有者 | 同上 |
| `run_closed` | run 已经收尾 | 把这个 run 挂着的审批在本地落成 expired |
| `invalid` | 校验不过，或毒帧 | 记日志 |

run 收尾后还放行的上行只有四种，登记在 `RUN_CLOSED_ACCEPTS`。`run_done` 本来就是条件写，重复了是空操作。`bot_text_done` 和 `bot_tool_call` 只把已经发生的事定稿，群里照实显示做到了哪一步。`work_append` 只看租约代际，同一台电脑在收尾前后写的条目都是 Pi 里真实发生的，拒收反而让镜像和服务器分叉。其余报文，比如 `approval_request`、`handoff`、`mention`，落在已收尾的 run 上一律 `run_closed`，被放弃的 run 不该再起新的动作。

信封落地后，三处旧补发一起删掉。它们是 `run_done_ack` 和代理里的 `unackedRunDones`，以及 `unsentLogins`。

### 3.3 下行至多一次，丢了由 hello 对账收尾

控制面用 `enqueueDownlink(tx, computerId, body, runId?)` 在调用方的事务里写 `agent_outbox`，序号取 `down_seq + 1`。决定和投递绑在一个事务里，派活提交了 prompt 就一定在发件箱里。连着的时候按序号推送。

电脑这一侧收到下行，先把游标写进 `.agent/downlink.json`，再交给运行器。下行处理器全是同步的，只入队，所以确认不会被一个 run 挂住。

游标落盘之后、交给运行器之前崩溃，这条下行就丢了。它由 hello 带的 `activeRuns` 对账收尾。控制面认为在这台电脑上开着、却不在 `activeRuns` 里的 run，按今天的 `finishMissingRuns` 收尾并在群里留一句「电脑断过线，这次活没做完」。prompt 还在发件箱里没送出去的 run 不算在内。

选至多一次而不是恰好一次，理由是同一个 prompt 跑两遍会把发布、发消息这类动作做两遍。丢一个 prompt 的代价是群里一句看得见的「没做完」。

发件箱不会无限长，靠下面几条规则。

- 绑了 `run_id` 的行在 `abandonRun` 的同一个事务里删掉，和 `finishRun` 一起。
- prompt 只发给在线或还在宽限里的电脑（见 4.3），离线很久的电脑不会积 prompt。不绑 run 的下行，比如 `publish_draft`、`browser_login`，也按同一条判断，电脑不在就照今天 `agents.send` 返回 false 的分支处理。
- `cancel{lane}` 按 (电脑, 道) 合并，只留代际最大的一条。
- 顶号时清空这台电脑的发件箱，删电脑时级联删。

### 3.4 握手顺序固定在一个函数里

1. 协议版本低于下限，回 4003。
2. 一个事务里做四件事。`conn_gen + 1`。hello 带的 `uplinkStream` 和 `up_stream` 不同就换流并把 `up_acked` 归零。续租并写 `install_id`。删掉 `down_applied` 及以前的下行行。
3. `finishMissingRuns`，排除 prompt 还没送达的 run。
4. 依次发 welcome（带 `upAcked`）、config、按 `bots.run_state` 的 pause 或 resume，然后重放发件箱。
5. `settleUnchargedRuns`。

重放排在 config 之后。今天 prompt 比 config 先到会报 `agent_error`，排在后面就不会。

每条上行带 `conn`，处理时和 `computers.conn_gen` 比，不等就丢，不回确认。旧 socket 里排队的帧在新连接 hello 之后才被处理，靠这一条挡住。

`pairLocal` 不再重置 `up_stream` 和 `up_acked`。同一台 Mac 重新配对会续用原来的流，服务器把游标清零会触发缺号死循环。新 Mac 是新的流，握手第 2 步自然归零。

### 3.5 版本握手只认一个整数

hello 加三个字段。`protocol` 是整数，`installId` 和 `piSessionVersion` 从 P3-10 起使用。今天的代理不带 `protocol`，按 1 算。hello 里已有的 `version` 字符串（`protocol.ts:74`）照旧只发不读。

P3-4 把协议定为 2，下限同时抬到 2，不做两套协议并存。用户只有自己团队，远程电脑随控制面一起部署，本机 App 收到 4003 按提示升级。之后每个改报文语义的单元，协议号和下限一起加一。

关闭码在 shared 的 `AgentCloseCode` 里（wt/p3-15 已提交）。4000 是被同一台电脑的新连接取代，4001 是 hello 不对，4002 是账号已删，4004 是被另一台 Mac 顶掉，4003 留给版本握手。桌面壳收到 4003 显示升级提示，并立刻查一次更新（P3-16）。

### 3.6 下行 cancel 不再等 run 自己跑完

两种 reliable 下行。`cancel{runId}` 停一个 run。`cancel{lane{botId, groupId}, epoch}` 停一条道，运行器只在本地代际小于目标代际时执行。租约换手时目标是新代际，删群、删 Bot 时发 `epoch + 1`，不加一的话这条 cancel 会被当成过时的忽略掉。

**放弃了什么。** 下行恰好一次，换成至多一次加对账。逐帧确认，换成累计确认。代理内存里的发件箱，换成落盘，代价是每条 reliable 上行最多多等一个 fsync 窗口。pause、resume 原本可以走可靠通道，现在留在 bare，握手时按 `bots.run_state` 整份重发（理由见 3.1）。新旧协议并存也放弃了，协议号不对的代理直接拒收（见 3.5）。

## 4. 租约让一个群同一时刻只在一台电脑上干活（P3-10）

### 4.1 租约记持有者，有效与否看电脑

`lane_leases(bot_id, group_id)` 记 `holder_computer_id`、`holder_install_id`、`epoch`。

租约是否有效不存在这一行上。有效的条件是持有电脑的 `computers.lease_until > now()`，并且 `holder_install_id` 等于 `computers.install_id`。一台电脑的所有道一起活、一起死，心跳只续 `computers` 一行。

`epoch` 只在持有者换人时加一。同一台电脑续用不加，本地镜像跨重启、跨 config 都可信。

持有者带 `installId`，因为 `computers` 按 (owner, kind) 唯一。P3-15 顶号之后，同一个 computerId 背后已经是另一台 Mac。`install_id` 由代理第一次启动时生成，存在 `.agent/` 下，hello 时带上。新 Mac 一连上，旧安装持有的租约全部失效，下一次派活接管时代际加一，旧 Mac 回来时镜像不可信，迟到的写入被挡在栅栏外。

### 4.2 一个时钟管断线收尾、接管和发件箱清理

今天的常量是心跳每 15 秒一次，45 秒收不到上行就判连接已死，断开后再等 15 秒宽限（`hub.ts:47-53`）。租约时钟由这三个数直接推出。

- 连着的时候，`lease_until = 最后一条上行 + 45 秒 + 15 秒`，每条上行续一次。
- 连接关闭时，`lease_until` 收到 `now() + 15 秒`，和今天宽限计时器到点是同一刻。

这一个值同时决定三件事，`abandonRun` 的断线收尾、租约能不能被接管、这台电脑发件箱里属于这些 run 的行何时删。三件事用同一个值，就没有「run 收了尾，租约还在」或者「租约过了，run 还开着」的中间态。

最坏情况是合盖，60 秒后可接管。正常断开是 15 秒。

宽限保留 15 秒，不改成底稿提的 60 秒。60 秒的理由是「短暂掉线不触发接管」，但没有数据支撑。接管还需要掉线期间这条道正好来了新活，而持有者回来后闲着的道可以迁回本机。保留 15 秒，`abandonRun` 的行为和它的测试都不用动。P3-4 里给断开和重连打点，攒两周的重连间隔再回头看。这个数列在「待确认」。

### 4.3 派活只有 `placeRun` 一个入口

`placeRun(tx, input, select)` 在调用方的事务里依次做四件事。

1. `claimLane`，一条条件 upsert，不先查后写。
2. 需要时 `takeOverLane`，代际加一，给旧持有者入队 `cancel{lane, 新代际}`。
3. `startRun`。
4. `enqueueDownlink`，发 `prompt{lane{epoch, heads}, …}`，`heads` 是这条道每条流在服务器上的 `{seq, head}`。

用户消息、Bot 之间的 @、例行、交接、牌桌的 `converge`、`hint`、`leave`，全部改调它。

| 情况 | 结果 |
| --- | --- |
| 持有者有效，道上有没收尾的 run | 粘住，派给持有者，排进它那条道的队列 |
| 道闲着 | 按选机偏好可以迁移，比如本机回来了，闲着的道迁回本机 |
| 持有者 `lease_until ≤ now()` 或安装标识对不上 | 接管，不论忙闲 |

选机只挑在线或还在宽限里的电脑。一台都没有时，照今天留一句提示，不建 run。底稿删掉了这条分支，让 prompt 留在发件箱里等。没采用，因为等的 prompt 到宽限一过照样随 run 收尾删掉，而电脑离线一周时发件箱会一直长。

### 4.4 三道栅栏挡住旧持有者

1. 上行 `work_append` 的条件写要求持有者和代际都对得上。
2. 模型请求 `/gateway/v1`、记录和附件 `/hub/v1`、MCP 代执行 `/mcp-proxy`，三处都校验请求头 `x-baize-lane`，值是 `<botId>/<groupId>/<epoch>`。网关 key 认出电脑，再查这台电脑是持有者、安装标识对得上、代际相等、`lease_until > now()`。三处共用一个校验函数。
3. 下行 `cancel{lane}` 等旧持有者回来时执行。

运行器在 Pi 的 `before_provider_headers` 钩子里给模型请求加这个头。`call_helper` 起的临时会话沿用父 run 所在道的头。

要求 `lease_until > now()`，是因为宽限已过、还没人接管的那段时间里，旧电脑不该再花用户的模型额度。

Pi 没有 pause，停不住一台断网的电脑。三道栅栏保证它断网期间做的事上不了服务器，也花不了模型额度。剩下的只有本机读写工作目录，和断网前已经开始的动作。

### 4.5 有后果的动作之前先同步记录

运行器在 `tool_call` 钩子里，闸门放行之后、执行之前，对动作类别不是 `read` 或 `write_workspace` 的调用做一次 `flush("before_effect")`。它把还没上传的条目传上去，包括带这次工具调用的那条 assistant 条目，并等到在当前代际下被确认。没东西可传就发一条空的 `work_append` 当探针。

- 被拒 `stale_epoch` 或 `not_holder`，这次调用记成 blocked，原因是「这个群已经换到另一台电脑上了」。
- 连接不在，或者等的时候断了，记成 blocked，原因是「和白泽断开了，这一步先不做」。

判断看连接状态，不设计时器。这样最贵的那种错，已经丢了租约的电脑再发一次布，就不会发生。代价是每次有后果的工具调用多一个往返。

**放弃了什么。** 挂着审批时租约不放（R4，见待确认）。更长的宽限。一条道多个持有者。

## 5. 工作记录存 Pi 原样的行，换电脑按它重建（P3-10、P3-11、P3-12）

### 5.1 存过滤后的原始行

`work_entries(bot_id, group_id, stream, seq)` 一行一条 Pi 会话条目。列有 `epoch`、`owner_id`、`run_id`、`entry_id`、`parent_id`、`pi_type`、`retention`、`line`、`search_text`、`visible_to`。`line` 是留存过滤之后那一行 JSONL 的原样字节，类型是 text。

`work_streams(bot_id, group_id, stream)` 是每条流的头，记 `next_seq`、`head`、`tail_entry_id`、`pi_session_version`。`stream` 分 `chat` 和 `table`，今天牌桌的角色一变就另开一份 Pi 会话，两条流对应两份会话。

追加是 `work_streams` 上的一条条件 UPDATE，要求 `next_seq` 等于帧里的起始序号，并且 `lane_leases` 的持有者和代际对得上，同一个事务里 INSERT 条目。这个事务也就是信封处理这条上行的事务。

存原样的行而不是白泽自己的格式，理由是重建时把这些行写回文件，交给 Pi 自己打开，中间没有任何翻译。自己的格式要跟住每个影响上游请求体的字段，文字签名、思考签名、决定何时自动压缩的 `usage`、模型戳，Pi 一升级就可能悄悄少一个。存原样的行，格式变化只表现为 `pi_session_version` 变了。

用 text 不用 jsonb，因为 jsonb 会重排键、去掉空白，写回的字节就不一样了，下面的哈希链也要逐字节算。

代价是服务器只能从 `pi_type` 和 `search_text` 看懂条目。`search_text` 要从 Pi 的消息形状里抽文字，这件事集中在 shared 的一个函数里，配用例。

会话文件的首行（Pi 的 SessionHeader）不上传。它带的 `cwd` 每台电脑不同，重建时就地生成。

### 5.2 哈希链头判断本地镜像可不可信

每条流用 shared 的 `advanceWorkHead` 按 `head_n = sha256(head_{n-1} ‖ sha256(line_n))` 往前滚，`‖` 拼接两个原始 32 字节摘要，空流用 `EMPTY_WORK_HEAD` 表示 32 个零字节。运行器对它上传的过滤后的行算链，每帧带上追加之后应有的头，服务器重算，对不上就回 `head_mismatch`，运行器下一次按服务器重建。

镜像可信的条件是本地 `lane.json` 的代际等于 prompt 带的代际，并且本地链在服务器的 `seq` 处的头等于服务器的 `head`。本地比服务器多出来的部分，是发件箱里还没确认的上传，照常补发。

只比条数不够。本地在追加之后、上传之前崩溃，或者孤儿尾巴被截掉又接上了别的条目，条数可能一样，内容已经不同。

### 5.3 留存过滤在上传前做，服务器再查一遍

运行器用 shared 的 `createRetainer` 按顺序过滤，每帧从已确认快照建立试算副本，只有服务器接受后才推进快照。服务器用 `checkFrame` 复查，不合规的整帧 `invalid`，旧版或有毛病的运行器推不上截图原图。规则三条。

- 图片块换成 `PRUNED_IMAGE_TEXT`，就是运行时裁旧截图用的那句「（之前的截图已省略）」（`bot-session.ts:100`）。重建之后模型看到的和今天看旧截图时一样。
- 超过 16 KiB 的文字块留头尾各 2 KiB，中间换成一行，写省略了多少字节和整段的 sha256。
- 「只在本机」的 MCP 连接的工具结果只留工具名、时间、字节数和 sha256（R1，见待确认）。服务器从自己的表里知道哪些工具名属于本机连接，查得出来。

`retention` 列标 `verbatim` 或 `redacted`。本地 JSONL 仍是原文，过滤只影响服务器上的那份和据它重建出来的会话。

### 5.4 上传靠 `getEntries()` 的尾部差分

Pi 的 `entry_appended` 对普通消息条目不触发。`agent-session.js` 在 `message_end` 之后调 `appendMessage`，这条路径不发这个事件。所以上传不能逐条挂事件。

`getEntries()` 只追加不改（`session-manager.d.ts:334`）。运行器在五个时刻对它做尾部差分。

1. `turn_end`。
2. `tool_call` 钩子里、请求审批之前，换电脑时快照里有这次挂着的调用。
3. `before_effect`，见 4.5。
4. `session_compact`，压缩条目一产生就上传。
5. `agent_settled`，在发 `run_done` 之前。

道上记着已上传的条数和最后一条的 id。`entries[uploaded - 1].id` 和记着的 id 不同，说明本地会话分了叉，停止上传，下一个 prompt 来时按服务器重建。

`work_append` 是 reliable 上行，带 `lane{botId, groupId, stream, epoch}`、起始序号、条目数组、追加后的头和 `cause`。`cause` 取 `turn_end`、`before_approval`、`before_effect`、`compact`、`settled`、`import` 之一。每帧最多 64 条。

### 5.5 本地镜像对不上就按服务器重建

`sessions/<groupId>/lane.json` 记 `{epoch, streams: {chat, table: {sessionFile, seq, head}}}`。Pi 的 JSONL 是缓存，这个文件说明缓存对应服务器上的哪一段。

prompt 来了先核对。可信就接着用本地文件。不可信就重建，按顺序走。

1. **补悬空调用。** 服务器尾部有 assistant 的工具调用却没有结果（上一台电脑执行到一半断了），先补一条合成的工具结果「结果未知，上一台电脑在这一步断开了」，作为普通条目在新代际下上传。之后谁再重建都有它。模型厂商不接受没有结果的工具调用。
2. **写文件重建。** 从 `GET /hub/v1/lanes/:botId/:groupId/:stream` 按 `seq` 分页拉全流，原子写成「新的首行加服务器的行」，再 `SessionManager.open(path, sessionDir, cwd)`。
3. **内存重建。** 打开失败时用 `SessionManager.inMemory(cwd, undefined, entries)`，没有本地文件，上传照常。
4. **冷启动。** 只在流的 `pi_session_version` 比本机 Pi 新，或者前两级都失败时用。开空会话，群里留一句「这台电脑读不了之前的记录」。

对不上的本地 JSONL 移进 `.stale/`，孤儿尾巴在那里。

快照给全流。从最后一次压缩开始的窗口暂时不做。Pi 的条目靠 `parentId` 串成树，缺了父条目的文件 Pi 收不收没有验证过。等 5.7 的等价测试证明它收，再做窗口。

### 5.6 第一次连上新控制面时导入旧会话

运行器收到每条 (Bot, 群) 道的第一条 prompt 时检查对应会话目录。有 JSONL 但没有 `lane.json` 的，就是旧会话。导入在这条道的串行任务中先于 prompt 执行；当前代际取自 prompt，config 不含群和租约，不在收到 config 时另扫全部群。

1. 把 `continueRecent` 会选中的那份复制到新路径，用 `SessionManager.open` 打开副本，Pi 在内存里做版本迁移，原文件不碰。
2. `getEntries()` 过 `createRetainer`，以 `cause: import` 上传。
3. 第一帧要求 `next_seq = 0`。没有租约行时必须带代际 1，服务器以 1 认领；已有租约且持有者是本机当前安装时必须带当前代际，追加后代际不变。其余情况拒收。后面的帧按当前代际继续导入。遇到非 ok 结果就停止这条道并记录原因；断线留到后续 prompt 再对账，不在原地循环。

按 (Bot, 群) 幂等。`next_seq` 已经大于 0 就拒收导入，本地文件留在原地，跑两遍结果相同。两台电脑都有同一个群的旧会话时，先到的赢，另一份留在本地，这和今天已经接受的分叉一样。旧文件一律不删。旧布局直接放在 `sessions/` 下的 JSONL 今天已经不续，导入也不管。

导入是这条道串行队列里的第一项任务，prompt 不会和它抢。

导入条目的 `visible_to` 按群定。牌桌群一律只给这个 Bot，因为今天的隐藏 run 只出自 `poker/converge.ts`、`hint.ts`、`leave.ts`，旧条目分不出哪条是隐藏的，按最严的算。其余群为 null，和那里的新 run 一致。

### 5.7 逐字等价测试守住 Pi 升级

两档，都在运行器测试里跑，上游是假的，不花钱。

- 没有截图、没有超长输出的会话。删掉本地会话目录，按服务器重建，下一次上游请求体和原会话会发的逐字节相同。这就是 P3-11 验证里「Pi 读到的历史和删之前一致」。
- 有截图或超长输出的会话。和原会话条目逐条过 `retainEntry` 之后的结果比。

存原样的行之后，这个测试不再是设计成立的前提，而是 Pi 升级时的回归护栏。

## 6. 运行器按 (Bot, 群) 分道，按 Bot 暂停（P3-9）

每个 Bot 一个 `BotRuntime`，下面挂各群的 `Lane`。

| 放在 Bot 上 | 放在道上 |
| --- | --- |
| 资源队列，管 MCP client、skill 目录、工具定义这类 Bot 级资源的对账 | 串行队列 `SerialQueue` |
| 暂停闸门 `PauseGate`，一停全停 | `chat` 和 `table` 两份 Pi 会话 |
| Bot 锁，浏览器和发布器共用，判断和执行各持一次，等审批时放开 | 正在跑的 run |
| 代际钉 `BotGeneration` | `propose_skill` 记的 runId、recall 结果、本地镜像 |

暂停的行为不变。闸门在 prompt 入场和每次 `tool_call` 前等，不 `abort()`。现在一个 Bot 的几条道都等同一个闸门。

审批闸门的键从 `callId` 改成 `(runId, callId)`。两条道可能同时挂着审批，两份 Pi 会话的 callId 不保证不重。

代际钉。每个 run 开始时钉住当时的 `BotGeneration`，即工具定义和设置。新 config 只为之后的 run 建新代际，旧代际在最后一个钉着它的 run 结束时释放。`applyConfig` 因此从不等道空闲。代际钉只管会话定义、设置和 MCP Client 的生命周期。连接和操作还在不在、要不要审批，每次调用前都按最新 config 判断，所以撤销在跑的 run 的下一次调用上就生效，被撤的报「已经不再提供这个操作」，已经开始的调用用钉住的 Client 跑完。牌桌道有 60 秒兜底和每秒的 sweeper，可能很少闲着，等它会让 config 迟迟生效。

停一条道的顺序固定。先把它挂着的审批落成 expired，再 abort 正在跑的 run，再 `session.abort()` 并丢掉排队的 prompt，最后释放会话、丢掉镜像、JSONL 移进 `.stale/`。这个顺序只用于停机和删 Bot 这类整道退出。下行 `cancel{runId}` 只动这一个 run，排队的丢掉，在跑的先把它挂着的审批落成 expired，等 Pi 写完过期结果再 `session.abort()`，会话和镜像都留着。

浏览器锁在等审批时放开。判断要不要审批时持一次锁，批准后重新取锁，复验当前页面和判断时是不是同一个，变了就拒绝执行。等审批期间同一个 Bot 在别的群的浏览器操作和发布器照常拿锁。

工作目录仍按 Bot，`<dataDir>/<botId>/work` 由它的几条道共用。P3-14 的隔离规则、系统提示里的路径、草稿和发布器都按 Bot 写，按群分目录会改掉产出落在哪。代价是同一个 Bot 在两个群同时改同一个文件会互相覆盖，这一期接受。

**放弃了什么。** 按群分工作目录。按道暂停。config 等道空闲再生效。

## 7. 审批有了作废和到期两种结局（P3-5）

P3-5 在 `.worktrees/p3-5-approval-rules` 里做，还没提交。下面按它的现状写。

**形状。** `ApprovalStatus` 加 `voided` 和 `timed_out`，`expired` 保持原义，指 run 收尾或电脑断线后审批失效。`Approval` 加 `deadlineAt`。下行 `approval_result` 的 `approved: boolean` 换成 `outcome`，取 `approved`、`rejected`、`voided`、`timed_out`。

**到期。** 控制面收到 `approval_request` 时定截止。run 的 `routineRunId` 非空，或者 run 的触发消息是交接卡，截止是建卡时刻加 10 分钟，否则为 null。用户当面发起的和 Bot 之间 @ 派的活都是 null，不按时间过期，24 小时提醒照旧。服务器每 15 秒扫一次，`UPDATE … SET status = 'timed_out' WHERE status = 'pending' AND deadline_at <= now RETURNING`，走 0029 的索引，给 run 所在电脑发结论，推 `approval_updated`。

**作废。** 用户的新消息路由到目标 Bot 之后、发 prompt 之前，控制面把这个 Bot 在这个群挂着的审批定为 `voided`，先给旧 run 所在电脑发作废结论，再派新活。`settleByReply` 先吃掉「批准」「同意」「拒绝」「不行」这类答复（`dispatch.ts:670` 的 `REPLY_DECISIONS`），吃掉了就不派活，也不作废。例行触发的消息不作废。别的 Bot、别的群的审批不受影响。

**运行器。**

| 结论 | 工具结果 | 之后 |
| --- | --- | --- |
| `approved` | 照常执行 | |
| `rejected` | 「归属人拒绝了这个动作。」 | 这一轮继续 |
| `timed_out` | 「10 分钟没人批，按拒绝处理。」 | 这一轮继续，Bot 可以告诉用户结果 |
| `voided` | 「用户发了新消息，这一步作废了。」 | 工具结果定下之后中止这个群的会话，旧 prompt 在 `agent_settled` 收尾，队列接着跑新 prompt |

**谁先写算谁的。** 写审批状态的有四处，按钮、群里答复、作废、到期扫描，全是 `WHERE status = 'pending'`。按钮抢输回 409，卡片写明结论和原因，「已作废 · 你发了新消息，这一步不做了」或「已拒绝 · 10 分钟没人批」。

**范围。** 只管审批。草稿和内容计划（`drafts`、`content_plans`）不受 10 分钟规则和作废规则影响。

**合入前要补的。** `decideApproval` 的条件写没查截止。截止已过、扫描还没到的那至多 15 秒里，点批准仍然生效。条件里补上 `deadline_at IS NULL OR deadline_at > now()`。

**和后续单元的关系。** P3-4 之后，作废结论和新 prompt 是同一个事务里写进 `agent_outbox` 的两行，靠序号保证先后。在那之前，靠同一条 WebSocket 上的发送顺序。P3-9 之后，一个群挂着审批不再挡这个 Bot 在别的群干活。P3-10 之后租约换手意味着旧 run 已被放弃，它的审批随 run 落成 `expired`，卡片写「电脑换了」。

**放弃了什么。** 暂停时冻结 10 分钟计时（R6）。审批行上单独存触发来源，现在从 run 推。草稿和内容计划的到期规则。

## 8. 偏好先出确认卡，点了才记（P3-6）

## 9. recall 现查现用，不进历史（P3-13）

Bot 调 `recall_memory(query)`，运行器带租约头请求 `POST /hub/v1/recall`，回 `{groupId, groupTitle, at, kind, excerpt}` 的列表。

查询条件写死。`bot_id` 是这个 Bot，`owner_id` 是归属人，`stream = 'chat'`，`visible_to IS NULL`，不搜当前群（它已经在会话里）。按相似度、再按时间排序。牌桌流、隐藏 run 的条目、别的 Bot 的条目在结构上就查不到，P3-13 验证里「牌友 Bot 查不到别人的底牌」钉的是这一条。

结果存在道上的 `recalls` 里。会话历史和服务器记录里只留一句「找到 N 条以前的记录，内容只在这一轮可见」。context 钩子改成 `pruneImages(expandRecalls(messages, recalls))`，只在这个 run 的请求里把这句换成命中的摘录，run 结束清空。

不写进历史，是为了删得掉。删群、删 Bot 时记录级联删除，下一个 run 起被删的内容就回不来。写进历史的话它会永久留在会话里。剩下删不掉的，是 Bot 转述进回复的话，那已经是群消息。

索引是 `search_text` 上的 pg_trgm GIN 部分索引，条件和查询一致，`stream = 'chat' AND visible_to IS NULL`。中文没有空格，pg_trgm 会把整句当一个词切三元组，短查询词按相似度可能命中很差。P3-13 先拿真实的中文群消息测命中，再定用相似度还是子串匹配，两种都能走同一个 trigram 索引。

依赖 P3-6 和 P3-10。

**放弃了什么。** 把结果写进历史或系统提示。跨 Bot 查。向量检索。

## 10. MCP 默认由控制面代执行（P3-7）

P3-7 在 `.worktrees/p3-7-mcp-proxy` 里做，还没提交。下面按它的现状写。

**形状。** `ToolConnection` 加 `localOnly`。`ToolConnectionConfig` 按 `localOnly` 分两支，`false` 不带 `authorization`，`true` 带。`listToolConfigs` 按电脑种类过滤，远程电脑收不到本机连接。config 加 `mcpProxy{baseUrl}`。

**代执行。** 运行器对非本机连接不建 MCP client，审批闸门照旧先过，再 `POST ${mcpProxy.baseUrl}/:connectionId/call`，请求体 `{botId, tool, arguments}`，Bearer 每次现取当前的网关 key，它在每次 hello 时轮换。回包 `{content, isError}`。控制面依次查连接归属、是否本机限定、是否 ready、Bot 是否分到、操作名是否存在，越权回 404，本机限定和待授权回 409。SDK client 按连接缓存，改、删、调用出错时作废。初始化和调用共用 60 秒上限，超时回 504。错误只回固定的中文分类，正文过 `redactCredential` 后才回电脑。

**只在本机。** 凭据只随 config 发给本机电脑，运行器直连，结果由运行器脱敏。进服务器记录时只留占位（5.3）。

用一次一调的 RPC，而不是把 Streamable HTTP 整条透传，理由是会话和凭据只在控制面一侧，运行器对代执行的连接根本不说 MCP，脱敏和超时只在一处。栅栏也只是查一个请求头。代价是 `tools/call` 之外的 MCP 能力不经代理，比如 resources、prompts、服务端通知。

**P3-10 之后。** `/mcp-proxy` 和网关一样校验 `x-baize-lane`。

**还缺的一块。** 本机连接的工具发现今天仍由控制面在建连接和补授权时做。对端只在用户 Mac 上可达时，比如 `127.0.0.1`，控制面连不上，发现会失败。目标是下行 `mcp_discover` 让本机电脑去探，上行 `mcp_discovered` 带回操作表，控制面只存。这块在 P3-7 收尾时做，计划里的验证文字没覆盖它，要补一条用例。

**放弃了什么。** 底稿的「AsyncLocalStorage 加自定义 fetch」备用路径。经代理使用 MCP 的非工具能力。OAuth。

## 11. 产物附件化，Bot 目录互相隔离（P3-8、P3-14）

### 11.1 附件存在 Postgres 里，按内容寻址（P3-8）

`attachments` 表记 `owner_id`、`bot_id`、`group_id`、`sha256`、`mime`、`size`、`bytes`（bytea），`(owner_id, bot_id, group_id, sha256)` 唯一，`bot_id` 和 `group_id` 带级联外键。

- `PUT /hub/v1/attachments` 带租约头上传。服务器重算 sha256，和声明的不同就拒，回附件 id。
- `GET /hub/v1/attachments/:id`，同一归属人的任何一台电脑都能取。
- `DraftImage` 加一支附件引用 `{attachmentId, sha256}`。起草时把配图传上去，另一台电脑上的发布器取下来、校验哈希再发。

工作记录不引用附件，截图在记录里只是一句占位。所以 P3-10 不依赖 P3-8。

存 bytea 而不是另起对象存储，理由是只多一张表。删除靠外键级联，P3-12 的「附件表里查不到残留」直接成立，备份还是一次 dump。代价是库随图片变大，所以单个附件要设上限，数值在 P3-8 里按现有草稿配图的实际大小定。

### 11.2 每个 Bot 只读得到自己的目录和共享区（P3-14）

已提交在 wt/p3-14-isolation（c05de62）。

- `ensureBotDirs` 同时建 `<dataDir>/shared`，系统提示给出它的绝对路径，要交给用户或别的 Bot 的文件放在那里。会话、记忆、技能和草稿仍在各 Bot 的私有目录。
- 闸门对 Pi 的 `read`、`write`、`edit` 先解析真实路径。落在数据目录里、却在本 Bot 目录和共享区之外的，直接拒，授权也放不开。工作目录或共享区里指向别的 Bot 的符号链接同样拒。共享区读写和工作目录一样免审批，草稿只读和浏览器禁区优先于共享区放行。
- seatbelt 在全局读规则之后先拒数据根目录，再放开本 Bot 目录的读和共享区的读写。工作目录和共享区的根用 `literal` 拒写，防止先删根再换成指向别的 Bot 的链接。bwrap 把共享区从屏蔽列表里排除。
- 删 Bot 时先关它的会话、浏览器标签和 MCP，再删 `<dataDir>/<botId>` 整棵目录，共享区保留。
- 设置页写明浏览器登录态由所有 Bot 共用。Chrome 的 profile 在 `<dataDir>/chrome-profile`，按电脑一份。

底稿把共享区叫 `.shared`，落地叫 `shared`。

**放弃了什么。** 按 Bot 分浏览器 profile，六.4 定了共用。对象存储。

## 17. 还没回答的问题

下面七条来自三份候选的盲评，三家都没答好。每条写卡在哪、倾向怎么做。

1. **两台电脑的 Pi 版本不同时怎么接管。** 卡在没有一处记版本。流上记了 `pi_session_version`，但 hello 和 prompt 都不带电脑的 Pi 版本，自动更新期间两台电脑会短暂不同。倾向是 hello 带 `piSessionVersion`，`placeRun` 只把道派给版本不低于这条流的电脑，没有合格的电脑就在群里提示升级，不建 run。冷启动只留给意外。

2. **递归触发链上的审批算谁发起的。** 例行触发 A，A 在多 Bot 群里 @ 了 B，B 的审批要不要 10 分钟到期。P3-5 现在按 run 自己的触发判，B 的 run 由 Bot 消息触发，截止为 null。卡在 `runs` 只记 `triggerMessageId`，消息上没有 run_id，一个回合的链只活在 `group-turn.ts` 的内存里。倾向是继承根触发源，由 `group-turn` 把根传进 `placeRun`，写进 run 行，到期判断改读它。要等 P3-10 有了 `placeRun` 再做。

3. **本机连接的结果换电脑后只剩占位，模型会不会重做有副作用的调用。** 卡在假上游测不出模型行为。倾向是占位写明「这一步已在本机执行过，结果不在这台电脑上」，并带工具名、时间、字节数和哈希。再加一个真模型的验收故事，换电脑后让 Bot 继续，看它是否重调。

4. **孤儿尾巴怎么处置。** 旧持有者回来时本地比服务器多出的条目，可能包含已经执行过的副作用。卡在旧代际的帧一律被挡，没有路径把它们的摘要送上来。倾向是另设一种 reliable 上行，只带工具名和次数，不带内容，不受代际栅栏限制，控制面把它写成群里一行「那台电脑失联期间还做了这些」。原文留在本机 `.stale/`。

5. **压缩摘要会不会把 recall 内容固化，让删除失效。** 卡在没验证 Pi 压缩时看到的是 context 钩子展开后的消息，还是会话里的占位。`session_before_compact` 给的是分支条目和准备数据，按它推断摘要只看到占位。倾向是 P3-13 加一条用例，删记忆后触发压缩，断言摘要里没有被删的内容。不成立就用 `session_before_compact` 的自定义压缩把 recall 段剔掉。

6. **`agent_outbox` 的增长上限，以及离线很久的电脑。** 这条有答案，写成了规则（3.3）。随 run 收尾删，只给在线或宽限内的电脑派活，`cancel{lane}` 按道合并，顶号清空，删电脑级联。还可以在 hello 时用 `activeRuns` 和已收尾的 run 求交集，现场生成 `cancel{run}`，不必入队，留作 P3-4 的可选项。

7. **牌桌道和聊天道共用一个 Bot 时，暂停和配置对账怎么办。** 代际钉让对账不等道空闲，暂停闸门同时拦两条道，牌友被暂停时 60 秒兜底替它出牌。卡在没核过 5336c6e 的 20 秒回执上限和 `converge` 是否默认一个 Bot 只有一条串行链。倾向是 P3-9 加用例，同一个 Bot 在牌桌和单聊同时有活时暂停、恢复、改配置，断言牌局照常推进、单聊按序。
